# chronos — 机群对时巡检与推演

面向几千台服务器的时钟同步工具：**持续巡检偏差 → 定位根因（本机 / 上游时间服务器 / 网络路径）→ 识别故障上游与波及面 → 推演闰秒影响 → 扫描业务代码里的墙上时钟陷阱 → 给出全机群对时配置建议**，并配套一个可视化页面。

背景的真实故障：一批机器的时间快了 4 分钟，分布式锁租约提前过期，两个进程同时持锁，订单被重复处理。根因是它们配的上游时间服务器自身不准；另有 VM 从暂停恢复后时间跳几十秒；还担心闰秒时"摊开"与"跳变"两种处置混用。

## 快速开始

```bash
# 1) 生成机群仿真数据（2400 台业务机 + 23 台时间服务器，21 天，含故障与一次闰秒）
python -m chronos gen --machines 2400 --days 21

# 2) 巡检 + 根因归因
python -m chronos analyze

# 3) 闰秒推演 + 业务影响清单
python -m chronos leap

# 4) 扫描业务代码里的墙上时钟用法
python -m chronos scan tests/corpus

# 5) 对时配置建议
python -m chronos advise

# 6) 与仿真真值对比评测
python -m chronos eval

# 7) 网页
python -m chronos serve      # http://127.0.0.1:5199

# 一次打印完整摘要
python -m chronos report
```

依赖：Python 3.9+、numpy、Flask（页面）。无其他外部服务。

## 仿真器如何贴近真实

仿真器不只产生"看起来像"的曲线，而是建模了时钟与 NTP 协议的真实机理：

- **晶振**：每台机器有固有频偏（TCXO ±2ppm / XO ±35ppm / 廉价 ±100ppm / 虚拟化 ±60ppm），围绕标称值做 OU 漂移，并按比例混入"坏晶振"。
- **NTP 伺服（PI 环）**：每步对上游测量 offset，`offset = 本机−对端 + 不对称/2 + 抖动`，用相位+频偏双环收敛；误差 >128ms 且允许 step 时直接跳变，禁用 step 的机器（`-x`/VM 默认）只能以 500ppm 慢追——所以一台 VM 落后 40s 要十几小时才追回。
- **多数表决（falseticker 剔除）**：客户端对多个上游取中位数，偏离中位数 >10ms 的视为说谎者剔除；只有当"被剔除者少于有效数一半"才采纳。**这决定了真实波及面**：一个说谎源在 ≥3 个独立源里会被剔除，但如果多个上游本身共因（都经同一坏源），表决失效——这正是单源/共因配置的危险所在。
- **网络路径**：每条链路有单程时延、去回不对称、抖动、丢包；拥塞故障按区域放大时延/抖动/丢包。
- **VM 暂停恢复**：恢复瞬间客户机时钟整体落后数十秒，之后按伺服规则追回。
- **闰秒**：按每台机器的策略（跳变/摊开/忽略）产生相对 UTC 的偏差分量。

> 仿真器刻意构建了一段"历史遗留区"：部分机器只挂一台单源中继，而该中继最终只依赖一台外部源 `ntp-c`。一旦 `ntp-c` 出错，这批机器就是共因故障的受害者——这是让故障波及面"可读"的关键。

## 1. 偏差巡检与根因归因

**检测**：按业务敏感度分级阈值（critical 5ms / high 50ms / standard 500ms / batch 2s），并额外要求至少 6σ 高于该机自身波动，避免敏感业务被正常抖动刷屏；需要连续越限 20 分钟以上才算一次事件。时间服务器统一收紧到 10ms。闰秒摊开窗口按"计划内"标记，绝不误报。

**归因**（三条互斥证据链，只用遥测不读真值）：

| 根因 | 判定依据 |
|------|----------|
| **网络** | 偏差窗口与路径时延/抖动/丢包恶化高度重叠，且同区域大量节点同步抖动 |
| **上游** | 与它共享某上游的兄弟在同一时段**同向、同幅**偏移；若该上游自身也偏，证据更强 |
| **本机** | 单步阶跃且同上游兄弟正常（VM 暂停/人工改时/ntpd 重启）；或长期单向漂移而兄弟正常（ntpd 停摆） |

实测（2400 台 / 21 天，与隐藏真值对比）：

- 故障机器 **召回 100%**，精确率 **80.5%**
- 根因归因准确率 **87.4%**（上游 94%、本机 100%、网络 100%）
- 剩余误报主要是良性的本机瞬变与阈值擦边，真值标注本身也难覆盖

> 精确率不是 100% 是诚实的：有些机器确实因晶振漂移、或未被注入的短暂事件而越限，真值集里没有对应"故障"，分析把它们判为"本机异常"并不算错。评测页把这一点透明列出。

## 2. 上游时间服务器故障识别与波及面

在 2400 台场景里，分析正确识别出：

- `ntp-c.pool` 自身 +240s → 直接带偏 86 台（其余 88 台被多数表决/冗余保护）
- 经单源中继 `relay-legacy-1` 二次传导 → 214 台
- `relay-legacy-1` 后来自身失联（holdover）→ 另一段独立事件，带偏 70 台，起始误差 50 分钟

检测起始时刻与真值的误差多为 **0**（正好在越限的第一个采样点）。页面上能看到"直连下游 / 实际带偏 / 被保护"的分解。

## 3. 闰秒推演

对正闰秒，四种处置的墙钟轨迹严格建模（`chronos/leap/policies.py`）：

- **step**：经典 Linux/ntpd SET——闰秒瞬间把时钟**向后拨 1 秒**，**时间倒流**、单调性破坏
- **slew**：内核在 1h 内线性摊掉，单调、无倒退
- **smear**：24h 抹平，单调、无倒退，但与真 UTC 长时间偏离
- **none**：完全不处理，永久快 1s

由此驱动四类业务原语的机理模拟，产出严重度矩阵：

| 原语 | step | slew | smear | none |
|------|------|------|-------|------|
| 分布式锁租约 | **致命** | 低 | 低 | 高 |
| 超时/重试 | 高 | 低 | 低 | 高 |
| 跨机日志排序 | 中 | 低 | 低 | 高 |
| 按时间生成编号 | **致命** | 无 | 无 | 高 |

**混用策略的灾难**（跨机事件时间戳排序）：`step+smear` 产生 2180 处跨机 >100ms 的严重逆序（基线仅 53 处）；`slew+smear` 因收敛窗口不同，也会在 21 小时内持续相差约 0.96s，产生 1384 处严重逆序。**结论：step 绝不能出现；slew 与 smear 也必须在全机群统一。**

页面"闰秒推演"标签给出完整业务清单（每策略 × 原语的指标、数值、严重度、说明）。

## 4. 业务代码墙上时钟扫描

AST + 函数级轻量数据流，识别：`sub_now`（墙钟相减算时长）、`timeout_wall`（墙钟做超时/到期比较）、`sleep_loop_wall`（墙钟轮询）、`deadline_wall`（`deadline = now + ttl`）、`timestamp_for_id`（墙钟生成编号），并能穿透别名、嵌套调用、`datetime.now().timestamp()`、`now = now or time.time()` 等。正确使用 `time.monotonic()`/`perf_counter()` 的不报。

在带人工标注的语料（`tests/corpus/`，含刁钻负例）上：**精确率 100% / 召回 100%**（注：语料与规则一同开发，属上界；真实代码预计会有一定漏报，规则已尽量保守）。

## 5. 对时配置建议

- **上游编排**：原则是"≥3 个真正独立的上游、散在不同 tier-1 源、至少 1 个跨区"。指出每台机器当前的问题（单源无法表决 / 多源但共因 / tier-1 多样性不足）并给出建议上游集合。当前机群有 486 台单源、317 台多样性不足。
- **闰秒策略**：全机群统一 smear（或统一 slew 1h，需与外部 UTC 对齐的系统用后者）；明确列出禁止事项与迁移步骤。
- **分级阈值**：按业务对时间的敏感度给出 5ms/50ms/500ms/2s 四档，配套观测窗口与处置动作。

## 设计取舍（诚实说明）

- **分析只用可观测遥测**（`dev_ms/delay/jitter/loss/reach/peer` + 拓扑），真值（`true_off_s`、故障掩码）只给评测用，确保评测有意义。
- **检测的精确率刻意不追求 100%**：宁可多报一点让运维核查，也不漏掉真实的时钟劣化。评测页透明区分"真值故障"与"背景漂移"。
- **VM 暂停与人工改时在纯遥测下难以 100% 区分**，统一归为"本机跳变"并在证据里给出判别线索，不硬凑子类。
- **小机群**（如 500 台）的上游波及面小，个别短时 holdover 可能不足以越限——这是物理真实（好晶振 23h 漂移可能不到 10ms），不是漏检 bug。
